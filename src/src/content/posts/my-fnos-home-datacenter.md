## 一、为什么会有一台这个东西

说来有点偶然。最开始只是手机存储反复告急，每次拍完照都要手动挑一遍删一批，烦了几年。后来又遇到一件更具体的事：想重温一部很早之前收藏过的纪录片，翻遍了所有平台，全部下架。

那一刻我意识到一件挺朴素的事——**放在别人服务器上的东西，随时可能消失**。会员会涨价，平台会下架，账号会被封，唯一确定的是数据不属于我。

于是开始看 NAS。前后犹豫了差不多两个月，主要纠结"是不是过度投入"。现在跑了一段时间回头看，结论很清楚：**这是我这几年买过最不后悔的东西**，而且它带来的改变远不止"存照片"这一件事。

## 二、硬件：一台不太贵的家用主机

先把配置摆出来，都是很平民的型号，没有任何服务器级的东西：

| 部件 | 型号 / 规格 | 当时的考虑 |
| --- | --- | --- |
| CPU | Intel Core i5-14500（14 核 20 线程，2.5GHz 起） | 带核显，影音转码基本不占 CPU |
| 内存 | 32 GB | 二十多个容器常驻之后，16G 会有点紧 |
| 系统盘 | NVMe 1 TB | 系统 + 存储池单独放，机械盘不用一直转 |
| 数据盘 | 3.6 TB 机械硬盘 | 冷数据、影音库 |
| 网络 | 千兆有线 | NAS 千万别用无线，这是硬规矩 |

**几个现在看来很对的决定：**

**第一，内存上到 32G。** 一开始觉得 16G 够了，结果容器一个接一个加上去之后，内存占用悄悄就上来了。现在 22 个容器常驻，`free -h` 里日常"已用"在 18G 左右，再加上文件缓存一截，32G 是刚刚好的状态。如果只能升级一处，我会选内存。

**第二，系统和数据分开。** NVMe 装系统和容器，机械盘存数据。好处是机械盘大部分时间可以休眠，整机安静、省电，而且系统盘坏了不会波及数据。

**第三，千兆有线，绝不用 Wi-Fi。** 我试过为了省事用无线连，结果内网传个几 G 的文件要等半天，还时不时会断。插上网线之后完全是另一个世界。

## 三、系统：为什么最后是飞牛 FnOS

前后试过几个方案，最后留下飞牛，原因很实在：

- **中文界面，而且不是翻译腔。** 菜单逻辑清楚，不用猜某个英文缩写是什么意思。
- **Docker 支持完整。** 可以直接用 Compose 部署，这点对我很重要——后面会说为什么。
- **相册、影视、下载这些刚需开箱即用。** 不用自己从零搭，省了大量时间。
- **没把命令行藏起来。** 想折腾的时候 SSH 进去就能用，不会被图形界面挡在外面。

## 四、现在机器上跑着什么

这是我目前常驻的服务（挑能说的讲）：

### 影音中心 · Emby

家庭影音的核心，端口 8096。电影、电视剧刮削得整整齐齐，海报墙、演员信息、字幕都对得上。电视、手机、平板都能直接连，家里人用起来零门槛。

以前看片子要在硬盘里翻文件夹，现在是打开就有海报墙，体验完全是两个时代的东西。

### 网盘挂载 · CloudDrive2

把云盘直接挂载成本地目录。我现在挂的是 115 网盘，挂上之后系统里多了一个 5P 级的"云上分区"——云盘里的东西可以像本地文件一样被 Emby 识别和播放，不用先下载到本地。对机械盘只剩大半空余的我来说，这等于把媒体库的上限直接抬到了"基本无限"。

### 内网穿透 · Cloudflared

Cloudflare 的隧道客户端。有了它，在外面也能访问家里的服务，不用在路由器上开端口，也不用公网 IP。**这是我后来才加的，加完之后整个 NAS 的使用场景完全变了**——从"家里的一个盒子"变成"随时随地能访问的个人云"。

### 媒体整理 · MediaTidy

自动整理媒体文件的命名和目录结构。以前手动改名改到崩溃，现在丢进去它自己处理完，Emby 那边直接就能正确识别。

### 其他几个

还有资源工具（resource-tool）、一个本地大模型 API 服务（freellmapi，跑在 3001 端口）、用来处理反爬的 FlareSolverr，以及 framebase 之类的辅助服务。这些属于"有用但不惊艳"的那一类，慢慢加进来的。

```bash
# 想看看机器上都有什么，就这一条
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
# 我现在这个数字是：22 个容器，其中 13 个常驻运行
```

## 六、踩过的坑，按代价排序

### 一号坑：用 Compose，不要用应用商店

这是我唯一想加粗强调的一条。

应用商店装东西很方便，点几下就好。但代价是：**配置散落在图形界面里，你看不见它们**。换机器、重装系统的时候，你得一个一个重新点，而且大概率想不起来当初是怎么配的。

用 Compose 之后，一个 `docker-compose.yml` 就是全部。备份是一个文件，迁移是一个文件，重建是一条命令。我现在所有服务都是 Compose 部署的，没有任何一个走商店。

### 二号坑：端口一定要先规划

我一开始随手映射端口，想到哪个用哪个。结果后来端口冲突到怀疑人生——某个服务起不来，查了半天发现是端口被另一个占了。

现在的习惯是：**每个服务分配端口前先记一笔**，反代用的端口和容器端口严格分开。顺便说一句，我博客用的是 18080，另外一些端口留给了反代服务，互不干扰。

### 三号坑：下载类服务一定要限速

别问我是怎么知道的。问就是某个深夜，家里人问"网怎么这么卡"。

### 四号坑：构建环境别用精简镜像

搭这个博客的时候踩到的：用 `node:slim` 镜像，容器里没 git，临时装又卡在国外源上动不了。换成完整镜像 `node:22-bookworm` 就好了——**它自带 git**。

类似的问题还出在字体上：构建时要从国外 CDN 下字体，容器里 DNS 慢导致超时。给容器指定国内 DNS（`223.5.5.5` / `119.29.29.29`）之后一次通过。

## 七、现在的存储使用情况

写这篇的时候我顺手 `df -h` 了一下，真实数据是这样：

| 位置 | 容量 | 已用 | 用途 |
| --- | --- | --- | --- |
| NVMe 存储池 | 754 GB | 622 GB（83%） | 系统、容器、Docker 数据、常用文件 |
| 机械盘存储池 | 3.7 TB | 162 GB（5%） | 影音库、冷数据、备份 |
| 云盘挂载 | 接近无限 | —— | 115 网盘，媒体库外挂 |

这个对比挺有意思——**快满的居然是 NVMe 那个池，3.6T 的机械盘反而只用了零头**。原因是容器和常用数据天然长在系统旁边，日积月累就上去了；机械盘里大部分是影音和备份，增长反而慢。

所以两件事我打算近期做：把 Docker 数据目录里能挪的大文件迁去机械盘；云盘挂载再利用起来，让"热门 + 冷门"的数据分层更清楚一点。

如果你问我该买多大的盘，答案还是那句：**比你以为需要的再大一档**。硬盘是这里面最不值得省的钱。

## 八、它到底改变了什么

用了这段时间，我发现最有价值的不是"省了网盘会员费"这种账面收益，而是三件更软的东西：

**第一，数据在自己手里了。** 照片、影片、文档都在自家硬盘上，不用看任何平台的脸色，不用担心哪天服务关停。

**第二，它变成了家庭基础设施。** 家里人现在会自然地打开电视看片子、在手机上翻相册，没有人需要知道背后是什么在跑。技术只有变成这样才算真的落地。

**第三，它给了我一个折腾的地方。** 这个博客就是跑在这台机器上的。想试什么新东西，开个容器试试，不行就删掉，成本几乎为零。这种"随时可以实验"的自由，是云服务商给不了的。

## 九、给同样想搞一台的人

如果你也在犹豫，我的建议非常具体：

1. **先搞，别纠结配置。** 一台二手小主机就能起步，用着用着你自然知道该升级什么。
2. **内存别省。** 32G 是舒服的起点。
3. **系统和数据分盘。** 后期省心非常多。
4. **所有服务用 Compose。** 这是给自己留后路。
5. **重要数据做冗余。** 单盘跑可以，但要想清楚它坏了你损失得起吗。

最后说一句：**折腾 NAS 最有意思的地方，不在于它省了多少钱，而在于数据终于回到自己手里了**。这句话听起来很老套，但真的遇到一次下架之后，你就懂了。

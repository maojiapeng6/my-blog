## 一、先说问题：为什么访问家里的服务这么麻烦

在家里，访问 NAS 上的服务很简单——浏览器打开 `192.168.10.110:8096` 就能看到 Emby。

但出了家门就不行了。原因是：**家里的设备没有公网可达的地址**，它们都在路由器的 NAT 后面，用的是 `192.168.x.x` 这种私有地址。外网根本不知道往哪儿发。

要让外网访问，就得解决这一层。

## 二、三种常见方案，以及我为什么不选前两种

### 方案一：端口映射（端口转发）

在路由器上配置：外网的 `公网IP:某端口` → 内网 `192.168.10.110:8096`。

**问题：**

- **需要公网 IP。** 很多宽带默认不给，要申请，而且可能是动态的，变了就访问不了。
- **等于把服务直接暴露在公网。** 任何人扫描到这个端口就能尝试访问，服务的每个漏洞都直接面对互联网。
- **HTTP 服务尤其危险。** 明文传输，中间人能看到所有内容。

### 方案二：传统内网穿透（frp 之类）

租一台有公网 IP 的服务器做中转，家里的服务主动连过去。

**问题：**

- 多一台服务器要维护，有成本
- 中转服务器的带宽成为瓶颈
- 配置和证书都要自己搞

### 方案三：Cloudflare Tunnel（我的选择）

核心思路很聪明：**不让外部连进来，而是让家里主动连出去。**

## 三、原理：为什么它不需要开任何端口

这是我觉得最优雅的地方。

传统方式是"外面的人敲门，我开门"。Tunnel 反过来：**家里的机器主动向外建立一条长连接，外网请求沿着这条已经存在的连接回来**。

```
家里的机器 ──主动出站──> Cloudflare 边缘节点
                              ↑
                         访客请求
```

因为连接是**由内向外**发起的，NAT 和防火墙天然允许这种流量——就像你访问网页一样，不需要在路由器上做任何配置。

**带来的直接好处：**

| 项目 | 端口映射 | Tunnel |
| --- | --- | --- |
| 需要公网 IP | 是 | **否** |
| 路由器开端口 | 是 | **否** |
| 服务直接暴露公网 | 是 | **否** |
| HTTPS | 自己配证书 | **自动签发** |
| 源站 IP 暴露 | 是 | **否** |

最后一条值得强调：**访客看到的是 Cloudflare 的地址，不是我家的 IP**。这意味着没人能直接对我的家宽发起攻击。

## 四、怎么配

### 1. 在 Cloudflare 上创建隧道

在 Cloudflare 的 Zero Trust 面板里新建一条 Tunnel，会拿到一个 token。

### 2. 在家里跑客户端

用 Docker 跑最省心：

```yaml
services:
  cloudflared:
    image: cloudflare/cloudflared:latest
    container_name: cloudflared
    restart: unless-stopped
    command: tunnel run
    environment:
      - TUNNEL_TOKEN=你的令牌
```

一条 `docker compose up -d`，容器起来就会自动连出去。

### 3. 配置域名与后端

在面板里加一条 Public Hostname：

```
子域名：blog.你的域名.com
服务类型：HTTP
URL：192.168.10.110:18080
```

**注意这里填的是内网地址和端口**——因为请求是从 Cloudflare 沿着隧道回来的，对它来说"内网"是可达的。

### 4. 完成

稍等一会儿，域名就能访问了，而且**自动带 HTTPS 证书**，不用自己申请和续期。

## 五、我用它做了什么

- **这个博客**：外网通过域名访问，后端指向 NAS 上的 Nginx 容器
- **家庭影音**：出门在外也能连回来看
- **其他自建服务**：按需加一条 Public Hostname 就行，不用动路由器

加了它之后，这台 NAS 的性质变了——**从"家里的一个盒子"变成"随时随地能访问的个人云"**。

## 六、几个要注意的地方

**第一，它不适合大流量。**

Cloudflare 的免费隧道有使用限制，不适合拿来做大文件分发或长时间高清视频流。我主要用于网页和轻量访问，重量级的还是走局域网。

**第二，源站还是要做好防护。**

虽然 IP 不暴露，但如果有人通过域名找到你，应用层的漏洞仍然存在。该更新的服务要更新，该设密码的要设。

**第三，访问控制可以用 Zero Trust 策略。**

可以给特定路径加访问策略（比如只允许指定邮箱登录），适合放一些不想完全公开的东西。

**第四，它依赖 Cloudflare。**

对方服务不可用时你的访问也会受影响。这是把便利交给第三方的代价，要有预期。

## 七、如果我没有公网 IP，还有别的选择吗

有，而且思路类似——都是"主动连出去"：

- **Tailscale / ZeroTier**：组网型，把设备虚拟到一个局域网里，适合自己远程管理
- **frp / ngrok**：自建中转或托管中转，灵活但要维护

我的判断标准很简单：**如果只是想让几个服务能被访问，Tunnel 最省事；如果想远程操作整台机器，组网工具更合适。**

## 八、一点延伸思考

折腾这个的过程中，我觉得最有价值的不只是"能访问了"，而是理解了一件事：

> **NAT 和防火墙挡的是"进来的连接"，不挡"出去的连接"。** 很多穿透方案本质上都是利用这个不对称性——从内部主动建连，再让数据沿原路返回。

理解了这一点，再看 frp、ngrok、Tailscale 这些工具，会发现它们的核心思路其实是一样的，区别只在于"谁做中转"和"怎么寻址"。

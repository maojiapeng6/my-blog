## 一、先说结论：全部用 Compose，不用应用商店

我这台机器上跑着 22 个容器，**没有一个是应用商店装的**，全部是 Compose 部署。

这不是洁癖，是被坑过之后的选择。

### 应用商店的问题

商店装东西很方便，点几下就好。但代价是**配置散落在图形界面里，你看不见它们**。

真正的问题出现在半年后：我想把某个服务换到另一个目录，发现记不清当初填了什么参数；系统重装之后，所有服务要一个一个重新点，而且大概率配得和原来不一样。

**配置看不见 = 无法备份 = 无法迁移 = 无法复现。**

### Compose 的好处

一个 `docker-compose.yml` 就是全部。

- **备份**：复制这一个文件
- **迁移**：到新机器粘贴，一条命令起来
- **复现**：配置文件在，服务就在
- **版本**：可以放进 git，改坏了能回退

对我来说，最后一点最重要——**配置能被版本管理，是自建服务从"玩玩"变成"正经基础设施"的分界线**。

## 二、我的目录结构

统一放在一个地方，每个服务一个目录：

```
/vol1/1000/docker/
├── Firefly/          # 这个博客
│   ├── docker-compose.yml
│   ├── src/          # 源码
│   ├── dist/         # 构建产物
│   └── nginx/        # 配置
├── emby-main/        # 影音
├── clouddrive2/      # 网盘挂载
├── cloudflared/      # 内网穿透
├── mediatidy/        # 媒体整理
└── ...
```

**规则很简单：一个服务一个目录，目录下必有 docker-compose.yml。**

这样做的好处是：想删某个服务，`rm -rf` 那个目录就干净了；想备份某个服务，打包那个目录就行。

## 三、端口规划：踩过最蠢的坑

### 我犯过的错

一开始随手映射端口，想到哪个用哪个。结果后来：

- 某个服务起不来，报 `port is already allocated`
- 查了半天，发现是另一个服务占着
- 改端口的时候又怕影响别的地方

**端口冲突是自建服务里最容易发生、也最难查的问题之一。**

### 现在的做法

**第一，先查再分配。** 拿到一个新服务，先看看端口有没有被占：

```bash
sudo ss -tlnp | grep :18080
```

**第二，反代端口和容器端口分开。** 容器自己监听的端口是一套，对外暴露的是另一套，中间通过反代连起来。这样以后换反代工具，容器不用动。

**第三，记一笔。** 我现在有个朴素的习惯：分配端口前先在备忘录里记一行。听起来很土，但真的能避免冲突。

> 顺便说：改端口只改**冒号左边**（宿主机端口），右边是容器里程序自己监听的，改了就连不上。

## 四、数据卷：决定你会不会丢东西

### 一句必须记住的话

**容器删了重建，容器内部的文件全没了。**

只有挂载出来的目录才会留在宿主机上。所以每个服务最重要的事是：**把需要持久化的目录挂出来**。

```yaml
volumes:
  - ./config:/app/config      # 配置，必须挂
  - ./data:/app/data          # 数据，必须挂
```

### 我踩过的坑

`./config:/app/config` 里的 `./` 是**相对于 docker-compose.yml 所在目录**，不是你当前敲命令的目录。

我早期因为搞混这个，把数据写到了一个意想不到的地方，找了半天。**现在我的习惯是：不确定就写绝对路径。**

## 五、出问题怎么查

这是我每天都会用的几条：

```bash
# 看看都跑着什么、状态如何
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

# 某个服务出问题，第一件事：看日志
docker logs --tail 50 容器名

# 实时跟日志（排查时最常用）
docker logs -f --tail 100 容器名

# 看资源占用，谁在吃内存/CPU
docker stats
```

**排查顺序我一般这样走：**

1. `docker ps` 看状态——是 `Up` 还是 `Restarting`？
2. 如果一直在重启，`docker logs` 基本能直接看到原因
3. 如果是端口问题，日志里会有 `address already in use`
4. 如果是权限问题，通常是挂载目录的权限不对

## 六、几个让我省了很多事的做法

### 1. 所有容器加 `restart: unless-stopped`

不加的话机器重启后容器不会自己起来，你会以为服务挂了。

```yaml
services:
  something:
    restart: unless-stopped
```

### 2. 日志设上限

不设的话日志会无限增长，我见过把磁盘吃满的情况：

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

### 3. 需要国内下载依赖的容器，指定国内 DNS 和镜像源

这个是搭博客时学到的：构建过程要从国外 CDN 下载东西，容器里 DNS 慢会导致超时失败。给容器指定 `223.5.5.5` / `119.29.29.29` 之后一次通过。

```yaml
dns:
  - 223.5.5.5
  - 119.29.29.29
```

### 4. 别用精简镜像做需要编译的事

我用 `node:slim` 踩过坑：它没带 git，构建时需要临时装，结果卡在国外源上动不了。换成完整镜像 `node:22-bookworm` 就好了。

## 七、内存是真实瓶颈

我现在的机器是 32G，22 个容器日常"已用"在 18G 左右，加上文件缓存还要再吃一截——**内存才是最先见底的资源**。

这个数字挺有参考价值的：如果你打算跑十个以上容器，**16G 会明显不够用**，32G 是舒服的起点。而且内存这东西很难后期"省"出来——服务越加越多，只会涨不会降。

```bash
# 看看谁最吃内存
docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}"
```

## 八、我最后沉淀下来的原则

折腾了这么久，真正留下来的就这几条：

1. **一切用 Compose。** 配置必须看得见、能备份、能进版本管理。
2. **一个服务一个目录。** 删得干净、搬得走。
3. **端口先查再分配。** 别嫌麻烦。
4. **需要留的目录全部挂出来。** 容器随时可能重建。
5. **所有容器加重启策略、设日志上限。** 两个小配置，省大麻烦。
6. **排查先看日志。** 九成的问题日志里都有答案。

## 九、写在最后

管理二十多个容器听起来复杂，但这套东西稳定下来之后，**我实际花在维护上的时间接近零**。

它们就那么跑着，偶尔看一眼 `docker ps`，全是 `Up`，然后关掉终端去做别的事。

我觉得这大概就是自建服务最好的状态：**配置的时候认真，配完之后忘掉**。
